# Shewah B2B

## Overview

Shewah B2B is a Next.js 14 admin panel designed for the Shewah jewelry business. It serves as a comprehensive B2B platform for managing various aspects of the jewelry business, from product catalog and order management to manufacturing tracking and partner relations. The platform aims to streamline operations, enhance collaboration with partners and manufacturers, and provide insightful analytics. Key capabilities include a public-facing design showcase, a material ledger, and robust notification systems.

## System Architecture

The application is built on Next.js 14 (App Router) and uses Supabase as its PostgreSQL database backend. Authentication is handled by NextAuth.js, supporting various user roles including master, sub, manufacturer, and retailer. Styling is implemented with Tailwind CSS, while Recharts is used for data visualization, and Lucide React for icons.

The system incorporates distinct portals for different user types:
- **Admin Panel**: Comprehensive management for master and sub users across various modules like analytics, CAD requests, catalog, orders, manufacturing, and vendor management.
- **Partner Design Portal**: A public-facing showcase for partners to browse collections, shortlist products, and express interest without requiring authentication.
- **Manufacturer Portal**: Provides manufacturers with a dedicated interface to manage orders, update status, add notes, and upload progress photos. Access to administrative functionalities is restricted.
- **Retailer Portal**: Offers retailers a view of the product catalog, custom design brief submission, and tracking of their own orders.

Key architectural features include:
- **Database Proxy**: All client-side Supabase interactions for authenticated users are routed through an `/api/db` proxy, leveraging the service role for enhanced security and RLS bypass for specific operations.
- **WhatsApp Integration**: Automated notifications for retailers on order status updates and for internal teams on CAD revision acknowledgements, utilizing configurable webhooks.
- **Material Ledger**: Tracks gold inventory and transactions with access control, ensuring gold integrity and consumption against orders.
- **CAD Management**: Comprehensive CAD request lifecycle, including partner sharing, revision tracking, and file uploads.
- **Cron Jobs**: Supports scheduled tasks like daily reconciliation digests for manufacturing partners, with email notification capabilities via Resend.
- **File Uploads**: Utilizes Cloudinary for storing various file types, including CAD files and reference images.

## Operations

- **Upload error retention**: The `upload_errors` table is trimmed by the `app/api/cron/cleanup-upload-errors` route, which deletes rows older than 90 days. Trigger it on a schedule (e.g. daily) with a `Bearer ${CRON_SECRET}` `Authorization` header, or manually as a master user. The Settings page only surfaces the most recent 100 rows, so older entries are not needed for live diagnosis.
- **Decimal precision for gold/diamond weights**: All weight columns (`products.gold_weight_g`, `orders.gold_weight_estimated/actual`, `manufacturing_orders.gold_weight_required/actual`, `material_transactions.quantity`, `material_float.current_quantity/reserved_quantity`, and matching `diamond_weight` columns) must be `numeric` so jewellers can record up to 4+ decimal places at every stage. If the live DB drifted and any of these are `integer`, run `scripts/migrate_task67_decimal_gold_weights.sql` in the Supabase SQL Editor — it inspects each column and only ALTERs the ones that aren't already `numeric`, so it is idempotent and safe to re-run. All gold-weight inputs in the admin UI use `step="0.0001"`.
- **Order deletion FKs**: `material_transactions.order_id` and `cad_requests.order_id` must be declared `ON DELETE SET NULL` so historical material-ledger rows and CAD requests survive when their parent order is removed. If deleting an order ever fails with `violates foreign key constraint`, run `scripts/migrate_task68_order_fk_cascades.sql` in the Supabase SQL Editor — it discovers, drops, and recreates each FK with the correct ON DELETE action, and is idempotent.
- **Catalog price refresh on gold-rate change**: Saving a new gold rate on `app/gold-rates` automatically calls `recomputeCatalogPrices()` (in `lib/supabase.ts`), which recomputes `trade_price`, `mrp_suggested`, and `karat_pricing` for every active product using the same formula as the catalog edit page (gold + labour + diamonds + making + IGI, then ×1.28 / ×1.40). Each repriced row is stamped with `priced_at_rate` (24K rate used) and `priced_at` (timestamp), surfaced as "Last priced at ₹X/g on <date>" on `/catalog` cards and on the product detail header. `/catalog` also exposes a master-only "Refresh catalog prices" button that re-runs the same helper on demand. The helper only writes when values differ and reports `{ updated, skipped, failed, pricedAt, error }` so partial failures surface in the alert. Run `scripts/migrate_task72_catalog_priced_at.sql` in the Supabase SQL Editor to add the two new columns; the writers fall back to the legacy 3-column update if the migration hasn't been applied yet.
- **Per-order payment ledger + due-payment reminder**: Every payment received is logged to `order_payments` (date, amount, reference, method, notes) and aggregated into `orders.advance_paid` / `balance_due` so legacy surfaces keep working. Dispatch flow in `app/orders/[id]/page.tsx` blocks on a balance > 0 and forces the admin to either log a payment or set `orders.payment_reminder_date` (today + N days). Once the reminder date passes and the balance is still non-zero, the order page surfaces a red "Payment overdue — confirm a new date" banner and the admin must use the Reschedule modal to enter a fresh date (after confirming with the retailer). The reminder date auto-clears the moment the order becomes fully paid. Run `scripts/migrate_task69_order_payments.sql` in the Supabase SQL Editor — it creates the table + index + RLS policy and adds the `payment_reminder_date` column to `orders`. Idempotent.
- **Central Stock is the single source of truth for raw-material inventory**: All gold (14K/18K/22K), diamond (LGD/natural), and finding movements are recorded in `stock_movements` and balances are SUMmed live by the `stock_balances` view — there is no on-hand column to drift. The `/stock` module exposes a dashboard, a full audit ledger at `/stock/movements`, and master-only `/stock/issue` + `/stock/receive` flows. Issuing gold or diamond to a karigar dual-writes: one `stock_movements` row (debits central) and one `material_transactions` deposit (credits the karigar's float), linked via `stock_movements.material_transaction_id`. Findings stay central-only. Direct deposits on `app/manufacturing/partners/[id]/float/page.tsx` are disabled — the Deposit tab now redirects to `/stock/issue?partner_id=...&material_type=...&amount=...` so the two ledgers can't diverge. Run `scripts/migrate_task70_central_stock.sql` in the Supabase SQL Editor (idempotent). The Vendors page is now suppliers-only — the old inventory tab and low-stock banner have been removed.
- **Landing page variant shipped (Task #96 — Outcome-First)**: The live `/` route is the "Outcome-First" variant from `artifacts/landing-mockups/src/components/mockups/OutcomeFirstVariant.tsx`. It was chosen over the Trust-First and Problem-First mockups because it (a) preserves the existing single-step `LeadForm` (multi-step would have rebuilt the form, fought the existing pixel/GA4 wiring, and overlapped with the in-flight "track step 2 dropoff" follow-up), (b) leads with the transparent-quote hook that maps cleanly to the copy already in `lib/landingCopy.ts`, and (c) avoids hardcoding fake testimonial names/headshots (a separate follow-up exists to collect real ones). The migration kept every user-facing string in `lib/landingCopy.ts` (the `VALUE_PROPS` entries gained an optional `metric` string used by the new card design, and section headings/eyebrows, the form-panel labels, the final CTA, the footer blurb, the mobile sticky CTA and the WhatsApp intro message all live there as well, exported as `SECTIONS`, `FORM_PANEL`, `FINAL_CTA`, `FOOTER`, `MOBILE_BAR`, `NAV`, `WHATSAPP_INTRO_MESSAGE`), preserved the `/partner-signup` form behaviour, the operator-editable WhatsApp number override, the Meta Pixel + GA4 wiring, and the floating WhatsApp button. The mockup sandbox at `artifacts/landing-mockups/` is left in place as a scratchpad for future design iterations.
- **Public partner-acquisition landing page (Task #85)**: The site root `/` is a public marketing landing page that captures inbound retailer leads — it is NOT the admin dashboard. The admin dashboard now lives at `/dashboard` (moved from `/`). Logged-in users are redirected from `/` to their role-appropriate home (`/dashboard` for admins, `/portal/manufacturer` or `/portal/retailer` for portal users) by `app/page.tsx`'s server-side `getServerSession` check. The login page also lands admins on `/dashboard`. The landing page (`app/LandingPage.tsx`) and full-page form (`app/partner-signup/page.tsx`) post to `app/api/public/partner-signup/route.ts`, an unauthenticated endpoint that uses the service role to insert into `partner_signups`. The endpoint applies a per-IP in-memory rate limit (5/min, 30/hr), a hidden honeypot field (`website`), captures UTM params + referrer + a salted SHA-256 IP hash, and fires both an email (Resend) and a WhatsApp (Meta Cloud API — reuses `META_WHATSAPP_ACCESS_TOKEN` / `META_WHATSAPP_PHONE_NUMBER_ID`) notification to ops via `lib/leadNotify.ts`. Per-channel dispatch outcome is persisted on the lead row so `/partners/leads` can show a green/red pill for each. All copy lives in `lib/landingCopy.ts` for one-place edits. Optional analytics: `NEXT_PUBLIC_META_PIXEL_ID` and `NEXT_PUBLIC_GA_ID` env vars enable Meta Pixel + GA4 (page-view auto-fired, `Lead` / `generate_lead` fired on submit). Recipient addresses live in the `settings` table (`lead_notify_email_to`, `lead_notify_whatsapp_to`, with on/off toggles `lead_notify_email_enabled`, `lead_notify_whatsapp_enabled`) so ops can change them without a deploy; `LEAD_NOTIFY_EMAIL` / `LEAD_NOTIFY_WHATSAPP_TO` env vars are used as fallbacks. Run `scripts/migrate_task85_partner_signups.sql` in the Supabase SQL Editor to provision the table — it is idempotent. The OG share image is generated dynamically by `app/opengraph-image.tsx` using `next/og` (no static asset needed). The admin lead inbox at `/partners/leads` lists every lead with status filters (new / contacted / qualified / onboarded / rejected), inline status changes, internal notes (saved on blur), tap-to-call / WhatsApp / email links, dispatch outcomes, and a "Convert to partner" link that pre-fills `/partners/new` from the lead. The Partners nav item shows an amber badge with the count of `status = 'new'` leads. AppShell's `isPublic` list now includes `/`, `/partner-signup`, and the existing portal/showcase/track routes — the admin chrome never wraps marketing pages.
- **Diamond shape & size catalog (Task #88)**: The diamond catalog at `/diamonds/catalog` ships with all 26 trade shapes pre-seeded — Round, Oval, Pear, Cushion, Princess, Marquise, Emerald, Radiant, Heart, Asscher, plus Baguette, Tapered Baguette, Trillion, Half Moon, Calf, Bullet, Tapered Bullet, Shield, Kite, Trapezoid, Hexagon, Epaulette, Carre, Rectangular Cushion, Rectangular Radiant, and Rose Cut. Each shape has its standard mm↔ct size grid populated from diamondsizecharts.com (round = single mm diameter, fancy = `"5x3 mm"` L×W labels with `approx_carats` as a reference weight per piece). The size grid is editable per-shape and feeds every dropdown in the app (orders, CAD specs, the diamond price matrix, retailer browse). Shapes in the left rail are grouped by category (Round / Square-cushion / Fancy-elongated / Side-stones-calibre / Antique-specialty) with a coloured badge showing each shape's size count. Masters can also "Copy sizes" from one shape to another via `POST /api/diamonds/sizes/copy` (skips duplicate labels). Run `scripts/migrate_task88_diamond_shape_size_seed.sql` in the Supabase SQL Editor — it relies on the unique index `diamond_sizes_shape_label_idx` from task 76 and is idempotent (`ON CONFLICT (shape_id, label) DO NOTHING`), so re-runs are safe.
- **Existing orders are NEVER repriced**: `recomputeCatalogPrices()` only updates the `products` table. Every order row stores its own `gold_rate_at_order` snapshot (captured at creation in `app/orders/new`, `app/catalog`, `app/catalog/collections/[id]`, and `app/api/portal/retailer/orders`) and its own `trade_price` / `total_amount`. The order edit form in `app/orders/[id]` always re-passes the existing snapshot, so editing an order never overwrites its locked rate. The detail page surfaces this with the "Gold rate locked: ₹X/g" line. If you ever add a new order-write code path, keep this guarantee — read `gold_rate_at_order` only at insert, never refresh it from `gold_rates`.

## External Dependencies

- **Supabase**: PostgreSQL database, authentication, and real-time features.
- **NextAuth.js**: Authentication library.
- **Tailwind CSS**: Utility-first CSS framework.
- **Recharts**: Composable charting library.
- **Lucide React**: Icon library.
- **Cloudinary**: Cloud-based image and video management (for file uploads, including CAD files).
- **Resend**: Email API for transactional emails (e.g., reconciliation digests).
- **WhatsApp Webhooks**: For sending and potentially receiving messages for notifications and acknowledgements.
